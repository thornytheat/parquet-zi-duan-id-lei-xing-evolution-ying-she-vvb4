业务背景、五条核心规则、演示步骤、六个业务模块与样例埋点（展开看长说明）

谁在用：湖仓表治理值班同学。上游（产出方）提 schema 变更单，下游（查询/看板/回刷任务）要求「别悄悄打断」。 当前靠人肉 diff 两个 schema JSON，改名和类型收窄经常漏判。 输入：旧 schema JSON + 新 schema JSON（fields: [id, name, type, nullable, default, partition]）、 数据文件清单 consumers.json（哪些文件/任务引用了哪些列）；可上传/粘贴，也可直接选内置 A/B/C 三组样例。

输出：字段匹配表（field_id 优先、名称兜底，逐条标出改名/ID 变化/新增/删除）、 类型判定（逐条给矩阵来源与结论 compatible / blocked / unknown）、 兼容级别（旧写新读 / 新写旧读双向 → full / backward / forward / none）、 迁移计划（ALTER 序列、回填对象、读写方升级顺序、broken_consumers）、 可下载迁移脚本，历史记录可回看、可重跑。

五条核心规则（后端真算，代码在纯函数模块里）

  • 1. 字段匹配 app/matching.py：field_id 相同优先认定为同一列；无 id 时按名称精确匹配。 id 同、名称变 → renamed；名称同、id 变 → id_changed（人工确认）； 无匹配 → added / removed。
  • 2. 类型矩阵 app/types.py：显式表：int8→int16/32/64、int32→int64、float→double、 decimal 精度提升 = 兼容；int64→int32、double→float、string→int、date→timestamp = 阻断；表外类型对一律 unknown，不猜。
  • 3. 兼容级别 app/compat.py：按「旧写新读 / 新写旧读」两个方向分别判定， 再合成 full / backward / forward / none；分区字段被删或改类型直接双向阻断。
  • 4. 迁移计划 app/migration.py：ALTER 顺序固定：改名 → 加列（含默认值）→ 回填 → 类型变更 → 删列最后；同时输出回填对象与读写方升级顺序，阻断项不产出 ALTER。
  • 5. 列引用检查 app/consumers.py：数据文件清单里引用了被删列、被阻断列的 → broken_consumers；引用改名列的 → 需同步改名（Parquet 按 id 仍可读）。

演示步骤（4 步走完主流程）

  1. 在工作台点「载入该样例」（或从总览点「用样例 B 执行对比」），工作台会预填旧/新 schema 与数据文件清单。
  2. 点「执行对比」→ 后端跑字段匹配、类型矩阵、双向兼容判定、迁移计划、列引用检查，写入一条运行记录。
  3. 结果页逐条看依据：字段 id 与名称变化、类型矩阵来源、兼容方向、ALTER 序列、回填对象、broken_consumers。
  4. 到「复核与导出」看历史、对比不同版本、下载 *.sql 迁移脚本；同一输入可反复重跑。
